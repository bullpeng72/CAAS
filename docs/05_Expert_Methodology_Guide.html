1.1.1 탄생 배경: 멀티 에이전트 시스템 개발의 5가지 어려움

AI 멀티 에이전트 시스템을 프로덕션 환경에 배포하는 것은 극도로 어려운 작업입니다. 2025년 현재, 대부분의 조직이 다음과 같은 문제에 직면합니다:

문제 #1: 복잡한 요구사항 → 구조화의 어려움

현실:

비즈니스 요구사항 (자연어)
"고객 문의를 자동으로 처리하고, FAQ를 검색하며,
필요시 담당자에게 에스컬레이션하는 시스템이 필요합니다."

       ↓ (개발자가 수동으로 변환)

구조화된 명세 (???)
- Agent 개수는? 역할은?
- Task 흐름은?
- 도구(Tools)는 무엇이 필요한가?
- 의존성 관리는?

문제점:
- 요구사항이 모호하고 불완전함
- 도메인 지식 부족 시 설계 오류 발생
- 명세 작성에 수일~수주 소요

문제 #2: Agent 설계의 전문성 요구

현실:

# 개발자가 직접 설계해야 함
from crewai import Agent

agent = Agent(
    role="???",  # 어떤 역할이 적절한가?
    goal="???",  # 명확한 목표 설정이 어려움
    backstory="???",  # 효과적인 backstory는?
    tools=[???],  # 어떤 도구를 할당해야 하는가?
    allow_delegation=???  # 언제 True/False?
)

문제점:
- CrewAI 전문 지식 필요
- Ontology (역할/도구 체계) 이해 필요
- 시행착오를 통한 최적화 필요 (수일 소요)

문제 #3: Task 의존성 관리의 복잡도

현실:

# 수동으로 의존성 그래프 구성
task1 = Task(...)
task2 = Task(context=[task1])  # task1 결과 필요
task3 = Task(context=[task1, task2])  # 둘 다 필요
task4 = Task(context=[task3])  # 순환 참조 위험!

# 문제: 의존성이 복잡해지면 관리 불가능

문제점:
- 순환 참조(circular dependency) 발생 위험
- 의존성 해결 순서 오류
- 병렬 실행 최적화 어려움

문제 #4: 품질 보증의 어려움

현실:

생성된 코드를 수동으로 검증:
- [ ] Python 문법 오류 없는가?
- [ ] CrewAI API 호환되는가?
- [ ] Tool이 정확히 할당되었는가?
- [ ] Task 의존성이 올바른가?
- [ ] 보안 위험은 없는가?
- [ ] 테스트 코드는 작동하는가?

→ 수동 검증 시간: 수시간~수일

문제점:
- 자동화된 검증 도구 부재
- 수동 검증의 높은 오류율
- 반복적 수정 작업 (75-83% 시간 소비)

문제 #5: 추적성(Traceability) 관리의 어려움

현실:

요구사항 변경 시 영향 범위 파악 불가:

요구사항: "FAQ 검색 기능 제거"
       ↓
영향을 받는 Agent는? → 수동 확인 필요
영향을 받는 Task는? → 수동 확인 필요
영향을 받는 Tool은? → 수동 확인 필요

→ 추적 시간: 수시간
→ 누락 위험: 높음

문제점:
- 요구사항 ↔ 코드 매핑 부재
- 변경 영향 분석 불가능
- 유지보수 비용 증가

CAAS의 비전: "자연어로 프로덕션급 멀티 에이전트 시스템 생성"

CAAS (CrewAI Agent Auto-generation System)는 위 5가지 문제를 해결하기 위해 탄생했습니다.

핵심 아이디어:

자연어 요구사항
      ↓
Golden Data (구조화된 명세)
      ↓
6-Phase Methodology
      ↓
프로덕션 코드 (main.py, agents.py, tasks.py, tools.py, tests)

CAAS의 약속:
1. ✅ 요구사항 → 코드 자동 변환 (5-10분 → 1-2분)
2. ✅ Agent 설계 전문성 불필요 (Ontology 기반 자동 설계)
3. ✅ Task 의존성 자동 관리 (순환 참조 자동 탐지)
4. ✅ 6개 Validator 자동 검증 (품질 보증 100%)
5. ✅ Traceability Matrix 자동 생성 (변경 영향 즉시 파악)

결과:
- 98.7% 구현률 (AGENT_BASED 도메인)
- 개발 시간 83% 단축
- 버그 수정 시간 75-83% 단축

상세 비교

1. LangChain / LlamaIndex
- 강점: 유연한 LLM 체인 구성, 풍부한 통합
- 약점: 개발자가 직접 Agent와 Task를 코딩해야 함
- CAAS 차별점: CAAS는 코드를 생성하고, LangChain은 개발자가 작성

2. AutoGPT / BabyAGI
- 강점: 자율적 목표 달성, 동적 Task 생성
- 약점: 코드 생성이 아닌 자율 실행, 프로덕션 배포 어려움
- CAAS 차별점: CAAS는 프로덕션 코드를 생성, AutoGPT는 실행

3. GitHub Copilot
- 강점: 코드 자동완성, 빠른 프로토타이핑
- 약점: 시스템 설계 불가, Agent 설계 지원 없음
- CAAS 차별점: CAAS는 시스템 전체를 설계, Copilot은 코드 조각 생성

4. CrewAI (Manual)
- 강점: 강력한 멀티 에이전트 프레임워크
- 약점: 개발자가 수동으로 모든 것을 설계 및 구현
- CAAS 차별점: CAAS는 CrewAI 코드를 자동 생성 (98.7% 구현률)

CAAS의 고유한 가치

CAAS만의 3가지 차별점:

  1. Specification-First: Golden Data라는 Formal Specification 기반
    - 모든 생성 결과가 명세에서 유래
    - 추적성 100% 보장
    - 변경 영향 분석 자동

  2. Domain-Driven: 17개 도메인별 최적화 코드 생성
    - CONVERSATIONAL_AI: 98.7% 구현률
    - DATA_ANALYSIS: 98.3% 구현률
    - 도메인 패턴 자동 적용

  3. Quality-First: 자동 검증 + 자동 수정
    - 6 Validators: Ontology, Golden Data, Dependency, Python311, CrewAI, Task
    - 3-Level Auto-Fixing: Template → Rule → LLM
    - Quality Gate: strict_quality_gates=True (v0.4.1)

1.1.3 CAAS의 핵심 철학 5가지

철학 #1: Specification-First

원칙:

"명세가 명확하면 코드는 자동화 가능하다."

구현:

자연어 요구사항
      ↓
Golden Data (Formal Specification)
      ↓
모든 Phase의 입력으로 사용
      ↓
생성된 모든 코드는 Golden Data에서 유래

Golden Data 구조:

class ConcretizedRequirement(BaseModel):
    """Golden Data = Formal Specification"""

    # 프로젝트 메타데이터
    domain: str  # 17개 도메인 중 선택
    project_name: str

    # 기능 명세 (계층적 구조)
    features: List[FeatureSpec]  # 5-15개 추천

    # 데이터 모델
    data_models: List[DataModel]

    # 경계 조건 (보안)
    boundaries: BoundariesSpec  # always/ask/never

    # 프로젝트 설정
    commands: CommandsSpec
    code_style: CodeStyleSpec
    git_workflow: GitWorkflowSpec

효과:
- ✅ 요구사항 → 코드 추적성 100%
- ✅ 변경 영향 분석 자동
- ✅ 반복 가능한 결과 (동일 입력 → 동일 출력)

async def execute_phase_with_retry(
    phase: int,
    max_retries: int = 3
) -> PhaseResult:
    """
    Phase 실행 with automatic retry

    Retry 전략:
    1. 동일 입력으로 재시도 (transient error)
    2. 입력 수정 후 재시도 (LLM Judge 피드백)
    3. Fallback to simpler approach
    """

    for attempt in range(max_retries):
        try:
            result = await execute_phase(phase)

            # Quality Gate 검증
            if quality_gate.passed(result):
                return result
            else:
                # LLM Judge 피드백으로 입력 개선
                improved_input = improve_input(
                    feedback=quality_gate.feedback
                )
                continue

        except Exception as e:
            logger.warning(f"Phase {phase} failed (attempt {attempt+1}): {e}")

            if attempt == max_retries - 1:
                raise PhaseExecutionError(f"Phase {phase} failed after {max_retries} attempts") from e

            # Exponential backoff
            await asyncio.sleep(2 ** attempt)

    자연어 → Golden Data 변환기

    Features:
    - HierarchicalFeatureExtractor (v0.3.0+)
    - 3-Strategy JSON Parsing
    - Domain-specific 최적화

    async def concretize(
        self,
        requirement: str,
        domain: Optional[str] = None
    ) -> ConcretizedRequirement:
        # 1. LLM으로 초안 생성
        draft = await self._generate_draft(requirement)

        # 2. Feature 계층 구조 추출
        features = self._extract_hierarchical_features(draft)

        # 3. Boundaries/Commands 자동 설정
        boundaries = self._infer_boundaries(features)
        commands = self._infer_commands(domain)

        # 4. Golden Data 생성
        golden_data = ConcretizedRequirement(
            domain=domain or self._classify_domain(requirement),
            project_name=self._generate_project_name(requirement),
            features=features,
            boundaries=boundaries,
            commands=commands
        )

        return golden_data

    """
    Agent Role 및 Task Type 기반 Tool 자동 할당

    1. Ontology에서 추천 Tools 가져오기
    2. Task Type과 Tool 호환성 검증
    3. 중복 제거 및 우선순위 정렬
    """

    # Ontology 조회
    recommended_tools = ONTOLOGY_RULES[agent_role]["recommended_tools"]

    # Task Type 호환 Tools 필터링
    compatible_tools = [
        tool for tool in recommended_tools
        if is_compatible(tool, task_types)
    ]

    return compatible_tools

class CodeGeneratorAgent(BaseExpertAgent):
    """Phase 5: 프로덕션 코드 생성"""

    async def execute(self, input_data: Dict) -> CodeGenerationResult:
        agents = input_data["agents"]
        tasks = input_data["tasks"]
        golden_data = input_data["golden_data"]

        # 1. 도메인 전략 선택
        domain = golden_data.domain
        strategy = self.code_engine.get_domain_strategy(domain)

        # 2. 코드 생성 (Jinja2 템플릿)
        code_files = await self.code_engine.generate_all_files(
            golden_data=golden_data,
            agents=agents,
            tasks=tasks,
            strategy=strategy
        )

        # 3. 3-Level Auto-Fixing 적용
        fixed_code_files = {}
        for filename, content in code_files.items():
            # Level 1: Template-based
            fixed = self.auto_fixer.fix_level_1(content)

            # Level 2: Rule-based
            if not self.validator.validate(fixed):
                fixed = self.auto_fixer.fix_level_2(fixed)

            # Level 3: LLM-based (필요 시)
            if not self.validator.validate(fixed):
                fixed = await self.auto_fixer.fix_level_3(fixed)

            fixed_code_files[filename] = fixed

        # 4. 정적 파일 생성
        static_files = StaticFileGenerators.generate_all(
            golden_data, agents, tasks
        )
        fixed_code_files.update(static_files)

        return CodeGenerationResult(
            code_files=fixed_code_files,
            output_dir=self.output_dir
        )

복잡도 점수 계산:

def calculate_complexity_score(
    feature_count: int,
    agent_count: int,
    task_count: int,
    dependency_depth: int,
    domain_count: int
) -> float:
    """
    복잡도 점수 계산 (0-100)

    - 0-30: 낮음 (단일 프로젝트)
    - 31-60: 중간 (모듈화)
    - 61-80: 높음 (다단계)
    - 81-100: 매우 높음 (분할 필요)
    """

    score = 0

    # Feature 개수 (0-25점)
    score += min(feature_count / 15 * 25, 25)

    # Agent 개수 (0-25점)
    score += min(agent_count / 7 * 25, 25)

    # Task 개수 (0-20점)
    score += min(task_count / 15 * 20, 20)

    # 의존성 깊이 (0-15점)
    score += min(dependency_depth / 4 * 15, 15)

    # 도메인 다양성 (0-15점)
    score += min(domain_count / 2 * 15, 15)

    return min(score, 100)

Microservices vs. Monolith 판단 기준

언제 Microservices를 선택하는가?

기준 Microservices 선택 Monolith 선택
팀 크기 10명 이상, 다중 팀 5명 이하, 단일 팀
Feature 개수 31개 이상 30개 이하
배포 빈도 주 1회 이상 월 1회 이하
확장 요구 부분 확장 필요 전체 확장 가능
도메인 복잡도 높음 (다중 Bounded Context) 낮음-중간
독립 배포 필수 불필요

- 확장: 제품 검색만 5배 확장 필요
→ Microservices 아키텍처 선택 ✅

Monolith 선택 예시:

프로젝트: 스타트업 MVP
- 팀: 1개 팀 (3명)
- Feature: 10개
- 배포: 월 1-2회
- 확장: 전체 2배 확장 가능
→ Monolith 아키텍처 선택 ✅

3가지 Execution Pattern 비교:

Pattern 주요 특징 Agent 구성 데이터 처리 적합한 도메인 구현률

"Be a good agent"  // ❌ 추상적

원칙 3: Task 요구사항 기반 검증

def validate_tool_assignment(agent: AgentSpecModel, tasks: List[TaskSpecModel]):
    """
    Agent의 Tools가 할당된 Task 수행에 충분한지 검증

    예시:
    - Task: "Search FAQ database"
    - Required Tool: "search_faq"
    - Agent Tools: ["search_faq", "chat_memory"] ✅
    """
    agent_tasks = [t for t in tasks if t.agent_id == agent.id]

    for task in agent_tasks:
        required_tools = infer_required_tools(task.description)
        if not all(tool in agent.tools for tool in required_tools):
            raise ToolMissingError(f"Agent {agent.id} missing tools for Task {task.id}")

Practice #1: Task 명세 작성 (Description, Expected Output)

Description (작업 설명):
- 원칙: 명확하고 실행 가능한 지시사항
- 길이: 20-50 단어
- 형식: 동사 시작, 구체적 액션

✅ Good Description Examples:

"Search the FAQ database using the customer's question as a query.

"Analyze the customer's sentiment based on their message text.

❌ Bad Description Examples:

"Do customer service"  // ❌ 너무 광범위

Expected Output (기대 출력):
- 원칙: 명확한 출력 형식 및 내용 정의
- 길이: 10-30 단어
- 형식: 데이터 구조, 포맷 명시

✅ Good Expected Output Examples:

"A list of 3 FAQ entries in JSON format: [{question, answer, relevance_score}]"

"A sentiment analysis result: {score: float, classification: str, confidence: float}"

"A professional customer response (200-300 words) with empathetic tone and clear answer"

❌ Bad Expected Output Examples:

"Good result"  // ❌ 형식 불명확
"Customer satisfaction"  // ❌ 측정 불가능
"Output"  // ❌ 내용 불명확

4.1.1 Quality Gate System 개요

Quality Gate란?

Quality Gate는 CAAS의 품질 보증 시스템으로, 각 Phase의 출력물이 다음 Phase로 진행하기 전에 품질 기준을 충족하는지 검증하는 게이트키퍼 역할을 합니다.

v0.4.1의 핵심 개선:

# caas_framework/agents/collaboration.py (v0.4.1)

# ❌ Before (v0.2.0-v0.3.0): 기본적으로 우회

strict_quality_gates: bool = True  # 품질 기준 미달 시 즉시 중단 🚨

왜 중요한가?

  1. 품질 보증: 저품질 출력물이 다음 Phase로 전파되는 것을 차단
  2. 조기 오류 발견: 나중 Phase에서 문제를 발견하면 수정 비용이 10배 이상 증가
  3. 일관성 확보: 모든 프로젝트가 동일한 품질 기준을 준수
  4. 추적성: 어느 Phase에서 품질 문제가 발생했는지 명확히 기록

4.1.2 QualityGateSystem 동작 원리

핵심 컴포넌트:

# caas_framework/quality/quality_gates.py

class QualityGateSystem:
    """
    Quality Gate Evaluation System (v0.4.1)

    Key Features:
    - ✅ AutoMetricsCollector 자동 통합 (v0.4.1)
    - ✅ 메트릭 누락 시 기본값 사용 (None → 0.0)
    - ✅ LLM Judge 타임아웃 (60초)
    - ✅ 무한 대기 버그 100% 해결
    """

    async def evaluate_gate(
        self,
        phase: AgentPhase,
        output: Any,
        context: Dict[str, Any]
    ) -> QualityGateResult:
        """
        Evaluate quality gate for a phase

        Args:
            phase: Current phase
            output: Phase output to evaluate
            context: Execution context (포함: code_artifacts, metrics)

        Returns:
            QualityGateResult with pass/fail status
        """
        # 1. Phase에 맞는 criteria 로드
        criteria = self._get_phase_criteria(phase)

        # 2. ✅ v0.4.1: AutoMetricsCollector로 자동 메트릭 수집
        if "code_artifacts" in context and not context.get("metrics"):
            from caas_framework.quality.metrics_collector import AutoMetricsCollector
            metrics = AutoMetricsCollector.extract_from_code(
                context["code_artifacts"]
            )
            context["metrics"] = metrics  # 자동 주입

        # 3. 각 criterion 평가
        results = []
        for criterion in criteria:
            result = await self._evaluate_criterion(
                criterion, output, context
            )
            results.append(result)

        # 4. 전체 점수 계산
        overall_score = self._calculate_overall_score(results)

        # 5. Pass/Fail 판정
        threshold = self.phase_thresholds.get(phase, 7.0)
        passed = overall_score >= threshold

        return QualityGateResult(
            phase=phase,
            passed=passed,
            overall_score=overall_score,
            criterion_results=results
        )

Completeness Score 계산:

def calculate_completeness(golden_data: Dict) -> float:
    """
    Calculate Golden Data completeness score (0-10)

    Weights:
    - Required fields: 30%
    - Feature specifications: 40%
    - Boundaries: 20%
    - Consistency: 10%
    """
    score = 0.0

    # Required fields (30%)
    required = ["project_name", "domain", "features", "agents_needed"]
    score += 3.0 * (sum(f in golden_data for f in required) / len(required))

    # Feature specs (40%)
    features = golden_data.get("features", [])
    if features:
        feature_completeness = sum(
            1 for f in features
            if all(k in f for k in ["description", "input", "output", "success_criteria"])
        ) / len(features)
        score += 4.0 * feature_completeness

    # Boundaries (20%)
    boundaries = golden_data.get("boundaries", {})
    if boundaries.get("in_scope") and boundaries.get("out_of_scope"):
        score += 2.0

    # Consistency (10%)
    if validate_domain_consistency(golden_data):
        score += 1.0

    return score

Validator 3: DependencyValidator

목적: Task 의존성 그래프 검증

검증 항목:
1. 순환 참조: Task 의존성에 순환(cycle)이 없는가?

def detect_cycles(tasks: List[Dict]) -> List[List[str]]:
    """
    Detect cycles in task dependency graph using DFS

    Returns:
        List of cycles (each cycle is a list of task IDs)
    """
    graph = {task["id"]: task.get("context_task_ids", []) for task in tasks}
    visited = set()
    rec_stack = set()
    cycles = []

    def dfs(node, path):
        visited.add(node)
        rec_stack.add(node)
        path.append(node)

        for neighbor in graph.get(node, []):
            if neighbor not in visited:
                dfs(neighbor, path.copy())
            elif neighbor in rec_stack:
                # Cycle detected!
                cycle_start = path.index(neighbor)
                cycles.append(path[cycle_start:] + [neighbor])

        rec_stack.remove(node)

    for task_id in graph:
        if task_id not in visited:
            dfs(task_id, [])

    return cycles

Best Practice:
- Task 의존성은 단방향 DAG(Directed Acyclic Graph)를 유지해야 함

def validate_syntax(code: str) -> Tuple[bool, List[str]]:
    """
    Validate Python syntax using AST

    Returns:
        (is_valid, error_messages)
    """
    errors = []
    try:
        tree = ast.parse(code)

        # Check for deprecated syntax
        for node in ast.walk(tree):
            # Example: Check for old-style string formatting
            if isinstance(node, ast.Mod) and isinstance(node.left, ast.Str):
                errors.append(
                    f"Line {node.lineno}: Old-style string formatting (%) is deprecated. "
                    "Use f-strings or .format()"
                )

        return len(errors) == 0, errors
    except SyntaxError as e:
        return False, [f"Syntax error at line {e.lineno}: {e.msg}"]

4.2.1 Auto-Fixing 개요

Auto-Fixing이란?

CAAS의 3-Level Auto-Fixing System은 검증 실패 시 자동으로 문제를 수정하는 계층적 시스템입니다.

3가지 Level:

Level 1: Template-based
  - 속도: ⚡⚡⚡ (밀리초)
  - 정확도: 70-80%
  - 사용: 간단한 패턴 수정

Level 2: Rule-based
  - 속도: ⚡⚡ (1-3초)
  - 정확도: 80-90%
  - 사용: 패턴 매칭 기반 수정

Level 3: LLM-based
  - 속도: ⚡ (10-30초)
  - 정확도: 95-99%
  - 사용: 복잡한 로직 수정

Fallback 전략:

Level 1 시도 → 실패 시 Level 2 시도 → 실패 시 Level 3 시도 → 여전히 실패 시 사용자 개입

async def fix(self, issues: List[Issue]) -> FixResult:
    """
    Hierarchical fixing strategy

    Try Level 1 → Level 2 → Level 3 in sequence
    """
    for issue in issues:
        # Try Level 1
        try:
            fixed = self.template_fixer.fix(issue)
            if self._validate_fix(fixed):
                return fixed
        except FixingError:
            pass

        # Try Level 2
        try:
            fixed = self.rule_fixer.fix(issue)
            if self._validate_fix(fixed):
                return fixed
        except FixingError:
            pass

        # Try Level 3 (last resort)
        fixed = await self.llm_fixer.fix(issue)
        return fixed

    self,
    project_dir: Path,

    Steps:
    1. Parse error log
    2. Categorize errors (8 types)

# caas_framework/agents/code_analysis_agent.py

def analyze_traceability(
    self,
    golden_data: Dict,
    code_artifacts: Dict[str, str]
) -> TraceabilityResult:
    """
    Analyze traceability: Golden Data Features → Code Implementation

    Returns:
        TraceabilityResult with completeness score
    """
    features = golden_data.get("features", [])
    traceability_matrix = []

    for feature in features:
        # Feature 키워드 추출
        keywords = self._extract_feature_keywords(feature)

        # 코드에서 키워드 검색
        implementations = []
        for filename, code in code_artifacts.items():
            if self._feature_implemented_in_code(keywords, code):
                implementations.append(filename)

        # Traceability 기록
        traceability_matrix.append({
            "feature_id": feature["id"],
            "feature_name": feature["name"],
            "implemented": len(implementations) > 0,
            "implementation_files": implementations,
            "completeness": self._calculate_feature_completeness(
                feature, implementations, code_artifacts
            )
        })

    # Overall completeness
    overall_completeness = sum(
        row["completeness"] for row in traceability_matrix
    ) / len(traceability_matrix) * 100

    return TraceabilityResult(
        matrix=traceability_matrix,
        overall_completeness=overall_completeness
    )

Feature 키워드 추출 (NLP):

def _extract_feature_keywords(self, feature: Dict) -> List[str]:
    """
    Extract keywords from feature specification

    Uses:
    - Feature name tokenization
    - Description NLP (spaCy)
    - Input/Output fields
    """
    keywords = []

    # Feature name
    keywords.extend(feature["name"].lower().split())

    # Description (NLP - extract nouns and verbs)
    import spacy
    nlp = spacy.load("en_core_web_sm")
    doc = nlp(feature.get("description", ""))
    keywords.extend([
        token.lemma_ for token in doc
        if token.pos_ in ["NOUN", "VERB"] and len(token.text) > 3
    ])

    # Input/Output
    keywords.extend(feature.get("input", "").lower().split())
    keywords.extend(feature.get("output", "").lower().split())

    return list(set(keywords))  # Unique

def _calculate_feature_completeness(
    self,
    feature: Dict,
    implementation_files: List[str],
    code_artifacts: Dict
) -> float:
    """
    Calculate feature implementation completeness (0-1)

    Criteria:
    - Agent defined: 30%
    - Task defined: 30%
    - Tool implemented: 30%
    - Integration in main.py: 10%
    """
    score = 0.0

    # Agent (30%)
    if any("agents.py" in f for f in implementation_files):
        score += 0.3

    # Task (30%)
    if any("tasks.py" in f for f in implementation_files):
        score += 0.3

    # Tool (30%)
    if any("tools.py" in f for f in implementation_files):
        score += 0.3

    # Integration in main.py (10%)
    main_code = code_artifacts.get("main.py", "")
    if any(keyword in main_code.lower() for keyword in self._extract_feature_keywords(feature)):
        score += 0.1

    return score

import json
from main import main as run_agent

def lambda_handler(event, context):
    """
    AWS Lambda handler for CAAS agent

    Trigger: API Gateway, EventBridge, SQS
    """
    try:
        # Input from event
        input_data = json.loads(event.get('body', '{}'))

        # Run agent
        result = run_agent(input_data)

        # Return response
        return {
            'statusCode': 200,
            'body': json.dumps({
                'success': True,
                'result': result
            })
        }
    except Exception as e:
        return {
            'statusCode': 500,
            'body': json.dumps({
                'success': False,
                'error': str(e)
            })
        }

GitHub Actions 예시:

# .github/workflows/deploy.yml

name: Deploy CAAS Agent

on:
  push:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Set up Python 3.11
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: |
          pip install -r requirements.txt
          pip install pytest pytest-cov

      - name: Run tests
        run: |
          pytest tests/ -v --cov=. --cov-report=xml

      - name: Upload coverage
        uses: codecov/codecov-action@v3

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Build Docker image
        run: |
          docker build -t my-registry/caas-agent:${{ github.sha }} .
          docker tag my-registry/caas-agent:${{ github.sha }} my-registry/caas-agent:latest

      - name: Push to registry
        run: |
          echo ${{ secrets.DOCKER_PASSWORD }} | docker login -u ${{ secrets.DOCKER_USERNAME }} --password-stdin
          docker push my-registry/caas-agent:${{ github.sha }}
          docker push my-registry/caas-agent:latest

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/caas-agent \
            agent=my-registry/caas-agent:${{ github.sha }}
          kubectl rollout status deployment/caas-agent

from collections import defaultdict
import logging

class ErrorTracker:
    """Track and categorize errors"""

    def __init__(self):
        self.error_counts = defaultdict(int)

    def record_error(self, error_type: str, error_msg: str):
        """Record an error occurrence"""
        category = self._categorize_error(error_type)
        self.error_counts[category] += 1

        logging.error(f"[{category}] {error_type}: {error_msg}")

    def _categorize_error(self, error_type: str) -> str:
        """Categorize error into buckets"""
        if "Import" in error_type:
            return "import_error"
        elif "Attribute" in error_type:
            return "attribute_error"
        elif "Timeout" in error_type:
            return "timeout_error"
        else:
            return "other_error"

    def get_summary(self) -> dict:
        """Get error summary"""
        total = sum(self.error_counts.values())
        return {
            "total_errors": total,
            "by_category": dict(self.error_counts),
            "error_rate": total / max(request_count._value.get(), 1)
        }
