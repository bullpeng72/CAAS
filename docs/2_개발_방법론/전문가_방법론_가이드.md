## 🎯 방법론 이론

### CAAS의 핵심 방법론 체계

CAAS는 세 가지 핵심 방법론을 통합하여 프로덕션 레디 코드를 생성합니다:

```
┌─────────────────────────────────────────────────┐
│         BMAD 6-Phase Methodology                │
│  (Build-Measure-Analyze-Deploy-Assure-Deliver) │
└─────────────────┬───────────────────────────────┘
                  │
         ┌────────┴────────┐
         │                 │
┌────────▼────────┐ ┌─────▼──────────┐
│   Spec-Driven   │ │      TDD       │
│   Development   │ │  Integration   │
└─────────────────┘ └────────────────┘
```

### 1.1 BMAD 방법론 (Build-Measure-Analyze-Deploy)

BMAD는 CAAS의 핵심 워크플로우로, 6개 Phase로 구성됩니다:

#### 이론적 배경

**BMAD**는 전통적인 소프트웨어 개발 생명주기(SDLC)를 AI 기반 코드 생성에 최적화한 방법론입니다:

1. **Build** (Phase 0-1): 요구사항 구체화 및 분석
2. **Measure** (Phase 2): 추적성 측정 및 검증
3. **Analyze** (Phase 3): 완전성 분석 및 설계
4. **Deploy** (Phase 4-5): 코드 생성 및 배포 준비

#### Phase별 품질 게이트

각 Phase 사이에는 **Quality Gate**가 존재하여 다음 Phase로의 진행 여부를 결정합니다:

```python
# caas_framework/agents/collaboration.py (v1.0.0 - 임시 우회)

async def _evaluate_quality_gate(
    phase: AgentPhase,
    output: Dict[str, Any]
) -> Optional[GateEvaluation]:
    """
    Quality Gate 평가 (v1.0.0: 임시 우회)

    v1.1.0에서 재활성화 예정:
    - Coverage 검증 (80% 이상)
    - Consistency 검증 (90% 이상)
    - Completeness 검증 (85% 이상)
    """
    # 현재는 우회되어 있으나, 향후 다음 기준 적용:
    # 1. Traceability Score >= 0.8
    # 2. Completeness Rate >= 0.85
    # 3. No Critical Errors
    pass
```

### 1.2 Spec-Driven Development (SDD)

#### 정의

**Spec-Driven Development**는 상세한 스펙(Specification)을 먼저 작성하고, 이를 기반으로 코드를 생성하는 개발 방법론입니다.

#### CAAS에서의 적용

```
요구사항 (Natural Language)
    ↓
Golden Data (구조화된 스펙)
    ↓
Agent/Task Spec (JSON)
    ↓
Architecture Spec (JSON)
    ↓
Production Code (Python)
```

**핵심 원칙**:
1. **스펙 우선**: 코드 전에 스펙을 완성
2. **추적성 보장**: 모든 코드는 스펙으로 추적 가능
3. **검증 가능성**: 스펙 기반 자동 검증

#### 실제 예시: Golden Data

```json
{
  "project_name": "E-Commerce Platform",
  "domain": "E_COMMERCE",
  "features": [
    {
      "id": "F001",
      "name": "사용자 인증",
      "description": "JWT 기반 로그인/로그아웃",
      "priority": "HIGH",
      "dependencies": []
    },
    {
      "id": "F002",
      "name": "상품 카탈로그",
      "description": "상품 검색, 필터링, 정렬",
      "priority": "HIGH",
      "dependencies": ["F001"]
    },
    {
      "id": "F003",
      "name": "장바구니",
      "description": "장바구니 추가/삭제/수량 변경",
      "priority": "MEDIUM",
      "dependencies": ["F001", "F002"]

  ],
  "non_functional_requirements": {
    "scalability": "10,000 concurrent users",

  }
}
```

### 1.3 Test-Driven Development (TDD) 통합

#### CAAS의 TDD 지원

CAAS는 코드 생성 시 자동으로 테스트 코드를 생성합니다:

```python
# 생성된 tests/test_agents.py 예시

import pytest
from src.agents import create_agents

class TestAgents:
    """에이전트 기능 테스트"""

    def setup_method(self):
        """각 테스트 전 실행"""
        self.agents = create_agents()

    def test_agent_creation(self):
        """에이전트 생성 테스트"""
        assert len(self.agents) > 0
        assert "user_auth_agent" in self.agents

    def test_agent_tools(self):
        """에이전트 도구 할당 테스트"""
        agent = self.agents["user_auth_agent"]
        assert agent.tools is not None
        assert len(agent.tools) > 0

    def test_agent_delegation(self):
        """에이전트 위임 설정 테스트"""
        for agent in self.agents.values():
            assert agent.allow_delegation is not None
```

#### TDD 사이클

```
1. 요구사항 분석 → 테스트 케이스 정의 (Phase 3)
2. 코드 생성 (Phase 5)
3. 테스트 실행 (Phase 5)
4. 실패한 테스트 → 코드 수정 (Gap Filling)
5. 모든 테스트 통과 → 배포 준비
```

#### Gap Filling (자동 보완)

```python
# Phase 5에서 누락된 기능 자동 보완
gap_analysis = {
    "missing_features": ["F015: Email Notification"],
    "missing_tools": ["email_tool"],
    "missing_tests": ["test_email_notification"]
}
```

## ⚠️ 알려진 문제 및 해결방법 (검증됨)

### 문제 1: ModuleNotFoundError - tools 모듈 import 실패 (✅ v1.0.3에서 완전 해결됨)

**2026-02-01 업데이트**: v1.0.3 Auto-Fix 기능으로 이 문제가 **완전히 해결되었습니다**!

**검증 결과**:
- ✅ Expert Agent 경로: `tools.py` (루트) + `from tools import ...` → 정상 동작
- ✅ Legacy LLM 경로: `src/tools.py` + `from src.tools import *` → 정상 동작

**이전 증상** (구버전):
```python
ModuleNotFoundError: No module named 'tools'
# 또는
ImportError: cannot import name 'file_read' from 'tools'
```

**이전 원인** (구버전):
- 코드 생성 경로와 import 경로 불일치
- ~~잘못된 코드: `from tools import database, file_read, file_write`~~
- ~~올바른 코드: `from src.tools import database, file_read, file_write`~~

**현재 버전 사용 시** (v1.0.0+):
- ✅ **수정 필요 없음**: 자동으로 올바른 import 경로 생성
- ✅ Expert Agent 경로: `tools.py`와 `from tools import ...` 자동 일치
- ✅ Legacy LLM 경로: `src/tools.py`와 `from src.tools import *` 자동 일치

**구버전 사용 시** (v0.x):
1. tools.py 위치 확인:
   ```bash
   find . -name "tools.py"
   ```

2. import 경로 확인 및 수정:
   ```bash
   # tools.py가 루트에 있으면
   grep "from.*tools import" agents.py  # "from tools import" 확인

   # tools.py가 src/에 있으면
   sed -i 's/from tools import/from src.tools import/g' agents.py
   ```

3. 검증:
   ```bash
   python -c "from agents import create_agents; print('✅ Import successful!')"
   ```

### 문제 2: 완전성 검증 불일치

**증상**:
- 같은 코드에서 완전성 점수가 100%와 0%로 번갈아 나타남
- 검증 시스템이 "통과"하지만 실제 코드 실행 실패

**원인**:
- 검증 시스템 버그 (ComprehensiveValidationResult.needs_fixing 속성 누락)
- AST 파싱만 수행하고 실제 import/실행 테스트 안 함

**해결방법**:
```bash
# 검증 결과를 맹신하지 말고 반드시 수동 테스트
python -c "from agents import create_agents; agents = create_agents()"

```

### 문제 5: Dockerfile, kubernetes/ 선택적 생성

**증상**:
- 일부 배포 관련 파일이 생성되지 않음

**원인**:
- 배포 파일은 옵션에 따라 선택적으로 생성됨
- `--deployment-target` 옵션 필요

**해결방법**:
```bash
# Docker 배포 파일 생성
caas generate "..." --deployment-target docker

# Kubernetes 배포 파일 생성
caas generate "..." --deployment-target kubernetes

# 수동 작성도 가능
```

**생성되는 파일**:
- `src/crew.py`: ✅ 항상 생성됨
- `src/tools.py`: ✅ 항상 생성됨
- `Dockerfile`: 선택적 (--deployment-target docker)
- `kubernetes/*.yaml`: 선택적 (--deployment-target kubernetes)
